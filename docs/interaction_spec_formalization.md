# Interaction Specification Formalization

## 1. What Are We Building?

ViviDoc generates **interactive animations** embedded in educational documents. Each knowledge unit may contain an interactive visualization — a slider that changes a circle, a dropdown that swaps objects, a drag interaction that simulates rolling, etc.

Currently, these are described in pure natural language (`interaction_description`). This document proposes a simple, structured specification that replaces free-form text with a clear decomposition.

## 2. What Is an Interactive Animation?

At the most fundamental level, any interactive animation consists of exactly three things:

```
InteractiveAnimation = (S, R, T)
```

| Component | Name | Meaning |
|-----------|------|---------|
| **S** | State | The data behind the screen — variables, their types, and how they relate |
| **R** | Render | How state becomes visuals — what you see on screen |
| **T** | Transition | How user actions change the state — what happens when you interact |

This is not a restriction or an approximation. It is what "interactive animation" **means**. Every interactive visualization, from a simple slider to a complex simulation, has state, renders that state visually, and responds to user input by changing state.

For educational visualizations specifically, we add one more element:

| **C** | Constraint | What must always remain true — the pedagogical invariant the visualization is designed to teach |

This gives us:

```
EducationalInteractiveVis = (S, R, T, C)
```

## 3. Connection to Munzner's Framework

Tamara Munzner's *Visualization Analysis & Design* (2014) decomposes visualization design into three questions: **What**, **Why**, and **How**. Our (S, R, T, C) maps directly onto her framework:

```
Munzner                         (S, R, T, C)
───────                         ────────────
What  — what data?          →   S  — what state exists?
How   — visual encoding?   →   R  — how is state rendered?
How   — interaction idiom? →   T  — how do user actions change state?
Why   — user's task?        →   C  — what should the learner observe?
```

The key difference: Munzner's framework is **descriptive** (for analyzing existing visualizations). Ours is **prescriptive** (for specifying visualizations to be generated by an LLM).

Munzner's "Why" layer asks "what task is the user performing?" (e.g., compare, identify trends, find outliers). In an educational context, this becomes "what should the learner discover?" — which is exactly what our constraint C captures. For example, the **Why** of a π visualization is "discover that C/D is constant regardless of circle size," which becomes `C: ratio ≈ π for all r`.

## 4. Concrete Example

### Natural language (current)

```
"The reader can adjust the radius of a circle using a slider, and as
the radius changes, the visualization updates the circle in real time
while recalculating and displaying the circumference, the diameter,
and the resulting ratio between them, allowing the reader to see
directly that the ratio stays roughly the same."
```

### Structured (S, R, T, C)

```json
{
  "state": {
    "r": { "control": "slider", "range": [0.5, 5], "default": 1 },  
    "C": { "derived": "2 * π * r" },
    "D": { "derived": "2 * r" },
    "ratio": { "derived": "C / D" }
  },
  "render": [
    "A circle whose size reflects r",
    "Labels showing the current values of C, D, and ratio"
  ],
  "transition": [
    "Dragging the slider changes r; C, D, and ratio update automatically"
  ],
  "constraint": "ratio ≈ 3.14159 regardless of r"
}
```

The structured version makes explicit what the natural language version leaves implicit:
- **What variables exist** and how they relate (S)
- **What appears on screen** (R)
- **What the user can do** and what happens (T)
- **What the learner should notice** (C)

## 5. More Examples

### KU2: Comparing circles of different sizes (static)

```json
{
  "state": {
    "circles": { "control": "none", "value": [
      { "r": 1 }, { "r": 2 }, { "r": 3 }, { "r": 5 }
    ]},
    "ratios": { "derived": "for each circle: C/D" }
  },
  "render": [
    "Several circles of different sizes displayed side by side",
    "Each labeled with its C, D, and C/D ratio"
  ],
  "transition": [],
  "constraint": "All ratios are approximately equal to π"
}
```

Note: no interaction (T is empty). This is a **degenerate case** — a static visualization is simply an interactive one with no transitions. The framework handles it naturally.

### KU3: Rolling an object to measure π

```json
{
  "state": {
    "object": { "control": "dropdown", "options": ["coin", "plate", "wheel"] },
    "diameter": { "derived": "lookup(object)" },
    "drag_distance": { "control": "drag", "range": [0, "max"], "default": 0 },
    "approx_C": { "derived": "drag_distance" },
    "approx_ratio": { "derived": "approx_C / diameter" }
  },
  "render": [
    "The selected object shown at rest",
    "A horizontal track showing how far it has been dragged",
    "Labels showing diameter, measured circumference, and computed ratio"
  ],
  "transition": [
    "Selecting from dropdown changes the object and its diameter",
    "Dragging the object along the track updates drag_distance and approx_C"
  ],
  "constraint": "approx_ratio approaches π as measurement accuracy improves"
}
```

## 6. Why This Matters for ViviDoc

### For the Planner
Instead of generating a blob of natural language, the Planner outputs structured (S, R, T, C). This is more constrained, which means:
- Less ambiguity for the Executor to misinterpret
- Easier for users to review and edit in the frontend

### For the Executor  
The Executor receives a clear contract:
- **S** tells it what variables and computations to implement
- **R** tells it what DOM elements / SVG / Canvas to create
- **T** tells it what event handlers to wire up
- The Executor's job becomes: synthesize code P such that P implements (S, R, T)

### For the Evaluator
**C** gives the Evaluator something concrete to check:
- Instead of "does the visualization look right?" (subjective)
- It can verify "does ratio stay ≈ π across different r values?" (objective, testable)

## 7. Expressiveness

Is **(S, R, T, C)** expressive enough to cover all educational interactive visualizations?

**(S, R, T)** is the definition of what an interactive animation *is*. Any system where:
- there is state,
- state determines what you see,
- user actions change state

...is by definition an (S, R, T) system. This covers:

| Pattern | Example | S | T |
|---------|---------|---|---|
| Parameter exploration | Slider changes radius | r ∈ ℝ | slider → r |
| Selection / filtering | Dropdown picks object | choice ∈ {a,b,c} | select → choice |
| Direct manipulation | Drag object along track | position ∈ ℝ | drag → position |
| Mode switching | Toggle between views | mode ∈ {A,B} | click → mode |
| Static display | Side-by-side comparison | constants | (none) |

The only interactive systems NOT covered are non-deterministic ones (random simulations), which are outside the scope of deterministic educational visualizations.

## 8. Summary

```
┌──────────────────────────────────────────┐
│     Interactive Animation = (S, R, T)    │
│                                          │
│  S: State      — what data exists        │
│  R: Render     — how data → visuals      │
│  T: Transition — how user → new state    │
│                                          │
│  + C: Constraint (educational invariant) │
│     "what the learner should discover"   │
│                                          │
│  Grounding: Munzner's What-Why-How       │
│    What → S, How → R+T, Why → C         │
└──────────────────────────────────────────┘
```

The value is not in proving a complex theorem. The value is in **structured decomposition**: replacing a blob of natural language with four clearly separated concerns, each serving a different stage of the pipeline (Planner → Executor → Evaluator).
